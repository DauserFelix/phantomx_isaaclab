3. BUG GEFUNDEN: velocity_limit VS. velocity_limit_sim IN phantomx.py (isaaclab_assets) —
   0.8 rad/s WAR NIE WIRKSAM, REAL WIRKSAM IST DER URDF-FALLBACK ≈5.6549 rad/s
--------------------------------------------------------------------------------

Ausgangsfrage: macht joint_velocity_limit_rad_s=5.65 im ROS2-Interface Sinn, oder ist 0.8 (der
in isaaclab_assets/robots/phantomx.py:97/104/111 stehende ImplicitActuatorCfg-Wert für alle 3
Aktuator-Gruppen) die richtige Referenz?

VERIFIZIERTE KETTE (gegen echten Isaac-Lab-Quellcode, /workspace/isaaclab/):
  1. phantomx.py setzt velocity_limit=0.8 (OHNE _sim-Suffix), velocity_limit_sim bleibt None.
  2. ImplicitActuator.__init__ (actuator_pd.py:81-91): da velocity_limit_sim None UND
     velocity_limit gesetzt ist -> Warnung geloggt ("previously ... not getting used by
     implicit actuators ... we continue to not use it") UND cfg.velocity_limit wird explizit
     auf None VERWORFEN.
  3. ActuatorBase.__init__ (actuator_base.py:180,192-194): da cfg.velocity_limit_sim None ist
     -> self.velocity_limit_sim wird auf den beim Konstruktor übergebenen USD-Wert gesetzt.
  4. articulation.py:1627: self._data.joint_vel_limits = root_physx_view.get_dof_max_velocities()
     — der beim USD-Import AUS DEM URDF übernommene Wert.
  5. full_phantom_isaacsim.urdf: <limit effort="2.8" velocity="5.6548668" .../> für alle 18
     Gelenke (Hardware-/AX-12A-Limit).
  6. articulation.py:1773: write_joint_velocity_limit_to_sim(actuator.velocity_limit_sim, ...)
     schreibt GENAU diesen URDF-Wert tatsächlich an den PhysX-Solver.

ERGEBNIS: PhysX begrenzt die reale Trainings-Gelenkgeschwindigkeit effektiv auf ≈5.65 rad/s,
NICHT auf die im Cfg stehenden 0.8 rad/s — ein stiller Bug im TRAININGS-Code selbst
(phantomx.py), unabhängig vom ROS2-Interface. Gleicher Bug-Typ wie mehrfach in der
Projekthistorie (hidden_dims, memory.replacement, totes movement_speed_x-Feld).

EMPIRISCHE GEGENPRÜFUNG anhand zwei echter Isaac-Lab-Traces (play.py --record_trace,

4. VOLLSTÄNDIGE ACTION-PIPELINE-ANALYSE: POLICY-OUTPUT -> GELENKBEWEGUNG, BEGRENZUNGEN JE STUFE
--------------------------------------------------------------------------------

User-Frage: was gibt die Policy aus, wie wird das zu joint_vel/Drehmoment, und ist das
begrenzt? Gegen echten Code (phantomx_thesis_env.py + Isaac-Lab-Actuator-Quellcode)
durchgegangen:

  1. Policy-Output: roher Skalar pro Gelenk (18), kein Drehmoment/keine Geschwindigkeit im
     Action-Space — reine Zielposition-Delta-Kodierung.
  2. Umrechnung (_pre_physics_step): q_target = q_def + action_scale*action, geklemmt auf
     q_def ± joint_pos_limit (bei strict_action_pipeline=True, aktuell PPO+SAC).
  3. set_joint_position_target() schreibt NUR einen Buffer (Docstring bestätigt: "does not
     apply ... only fills the buffers"), erst write_data_to_sim() -> root_physx_view.
     set_dof_position_targets() gibt es tatsächlich an PhysX weiter.
  4. PhysX (ImplicitActuator, "implicit" weil PhysX selbst die PD-Regelung übernimmt) berechnet
     intern Drehmoment ≈ Kp*(q_target-q_ist) + Kd*(0-q̇_ist), Kp=10.0, Kd=2.0.

BEGRENZUNGEN JE GRÖSSE:
  - Position: HART begrenzt (echtes torch.clamp in Python, joint_pos_limit=1.0 rad) —
    zuverlässig.
  - Drehmoment: HART begrenzt (effort_limit_sim, korrekt aus effort_limit=1.5 übernommen, KEIN
    _sim-Suffix-Bug hier) — PhysX kappt das PD-Drehmoment hart auf ±1.5 Nm.
  - Geschwindigkeit: NUR WEICH begrenzt — kein Software-Clip im Env-Code, sondern ein
    kraftbasiertes PhysX-Regelziel (velocity_limit_sim, siehe Punkt 3 für den tatsächlichen
    Wert). Laut Isaac-Lab-Doku "the physics engine will actually try to brake" — kein hartes
    Delta-Cap, kann kurzzeitig überschritten werden (erklärt die Ausreißer bis 30+ rad/s in den
    echten Traces trotz nominal niedrigerer Solver-Grenze).

9. ANALYSE (KEINE CODE-ÄNDERUNG): DREHEN AUF DER STELLE TRAINIEREN — MACHBARKEIT + AUFWAND
--------------------------------------------------------------------------------

User-Frage: kann die Spider trainiert werden, sich auf der Stelle (ohne Vorwärtsbewegung) nach
links/rechts zu drehen? Explizit als reine Analyse angefordert, kein Code.

BEFUND (gegen aktuellen Code verifiziert):
  - track_ang_vel_z_exp existiert bereits als eigener, von track_lin_vel_xy_exp unabhängiger
    Reward-Term — kein neuer Reward-Term nötig für die Grundidee.
  - movement_penalty (_compute_movement_penalty) prüft AUSSCHLIESSLICH commands[:,0] (vx) — bei
    vx=0 ist has_forward_command=False, velocity_deficit*0=0. Reines Drehen auf der Stelle wird
    NICHT durch die Movement-Penalty bestraft, kein Zielkonflikt an dieser Stelle.
  - yaw_rotation_speed_x existiert als Cfg-Feld, PPO-Curriculum setzt commands[:,2] bereits ab
    350k Schritten — ABER IMMER gleichzeitig mit commands[:,0]=max_speed (Kurvenlaufen), NIE mit
    vx=0. Das aktuelle Curriculum trainiert also Kurvenlaufen, nicht Drehen-auf-der-Stelle — ein
    wichtiger, eigenständiger Unterschied (biomechanisch näher an "Schwenken" als an Gehen, bei
    radialem Hexapod-Beinlayout vermutlich eigene Gangart nötig).
  - Analoges Kernel-Risiko wie beim historisch dokumentierten "Steht-statt-Geht"-Problem und dem
    nie umgesetzten Strafing-Plan (20.07.) plausibel: bei kleinem yaw_rotation_speed_x könnte
    Stillstehen bereits einen Großteil des maximalen track_ang_vel_z_exp-Rewards bekommen —
    vermutlich bräuchte es denselben Bootstrap-Trick (erst übertrieben hohes Yaw-Ziel, dann
    runtertransferieren) wie bei SACs BOOTSTRAP_SPEED.

DREI OPTIONEN BEWERTET (Aufwand/Risiko):
  1. Zusätzlich, separate Env-Cfg-Variante: mittlerer Aufwand, geringes-mittleres Risiko.
  2. Ins Gesamttraining integrieren (kombiniert mit Vorwärts-/Kurvenfähigkeit): höchster
     Aufwand, höchstes Risiko (Catastrophic-Forgetting-Gefahr, "zu viel gleichzeitig ändern" —
     historisch bereits mehrfach als Fehlerquelle identifiziert, siehe Log 07-09 Punkt 10).
  3. Bestehende Policy weitertrainieren (--resume_step + neue Curriculum-Phase am Ende):
     geringster Aufwand, technisch am saubersten vorbereitet (Infrastruktur existiert bereits
     seit Log 07-12), mittleres Risiko für Degradation der bereits gelernten Vorwärtsfähigkeit.

EMPFEHLUNG: Option 3 als pragmatischster Einstieg, Option 2 eher nicht als ersten Schritt.
Offener Punkt: Kernel-Breite (ang_vel_kernel_width) bei kleinem Yaw-Ziel vor Umsetzung
durchrechnen (analog zur historischen lin_vel-Kernel-Rechnung), um zu wissen ob ein
Bootstrap-Trick von Anfang an nötig ist. NICHT UMGESETZT, nur analysiert.
