SIMULATION TIMING
--------------------------------------------------------------------------------

  sim.dt      = 1/200 Hz = 0.005 s     (Physik-Step)
  decimation  = 4                       (Policy lauft jeden 4. Physik-Step)
  policy_dt   = 0.005 x 4 = 0.020 s   -> 50 Hz

  step_dt = 0.02 s wird fuer Reward-Skalierung verwendet.

KOORDINATENSYSTEM (Body Frame)
-------------------------------

  x -> vorwaerts (Fahrtrichtung)
  y -> links
  z -> oben

  Alle Velocities und der Gravity-Vektor sind in diesem body-fixed frame.
  Er rotiert MIT dem Roboter — bei Drehung des Roboters rotieren die Werte mit.

GRAVITY-VEKTOR — BEISPIELWERTE
--------------------------------

  Zustand                    gravity_b
  -------------------------  ---------------------
  Roboter gerade stehend     [ 0.0,  0.0, -1.0 ]
  45 Grad nach vorne geneigt [ 0.7,  0.0, -0.7 ]
  45 Grad nach links geneigt [ 0.0, -0.7, -0.7 ]
  90 Grad auf der Seite      [ 0.0,  1.0,  0.0 ]
  Umgekippt (kopfueber)      [ 0.0,  0.0, +1.0 ]

  Berechnung in Isaac Lab:
    gravity_b = R_body_from_world.T @ [0, 0, -1]

  Berechnung aus IMU (nur korrekt bei a_body ≈ 0):
    gravity_b = -a_imu / |a_imu|

  Bessere Methode fuer Gazebo (wenn IMU Quaternion liefert):
    from scipy.spatial.transform import Rotation
    q = [msg.orientation.x, msg.orientation.y,
         msg.orientation.z, msg.orientation.w]
    rot = Rotation.from_quat(q)
    gravity_b = rot.inv().apply([0.0, 0.0, -1.0])

PIPELINE: POLICY-OUTPUT -> PHYSIK
-----------------------------------

  Policy-Output (raw float, unbegrenzt, z.B. -40 bis +58 bei schlechter Policy)
       |
       v  Step 1: clamp(x, -1.0, +1.0)
  Geclippte Action  in [-1, 1]
       |             (wird als last_actions in der NAECHSTEN Obs gespeichert!)
       v  Step 2: x * action_scale  (action_scale = 0.5)
  Skalierter Offset  in [-0.5, +0.5] rad
       |
       v  Step 3: + default_joint_pos
  Zielposition  (z.B. femur: 0.5 +/- 0.5 => 0.0 bis 1.0 rad)
       |
       v  Step 4: clamp(q_def - joint_pos_limit, q_def + joint_pos_limit)
  Finale Zielposition  [rad]       joint_pos_limit = 0.5235 rad (= 30 Grad)
       |
       v  PD-Regler: Kp=10 Nm/rad, Kd=2 Nm*s/rad
  Drehmoment  (begrenzt auf 1.5 Nm, Geschwindigkeit auf 0.8 rad/s)

LAST_ACTIONS — GENAUE SEMANTIK
--------------------------------

  Reihenfolge innerhalb eines Policy-Steps in Isaac Lab:

    1. Policy erhaelt obs_t
    2. Policy gibt action_t aus
    3. _pre_physics_step(action_t):
         self._actions = clamp(action_t, -1.0, 1.0)     <- hier wird gespeichert
         processed = default + 0.5 * self._actions
    4. Physik-Step laeuft (4x fuer decimation=4)
    5. _get_observations():
         obs = [..., self._actions]   <- enthaelt den AKTUELLEN geclippten Output

  -> last_actions[48:65] ist der geclippte Output des AKTUELLEN Steps,
     nicht des vorherigen.

  Im ROS2-Node muss after dem Publishen gesetzt werden:
    self.last_actions = np.clip(actions, -1.0, 1.0)   <- KORREKT
    (nicht davor, nicht nach dem naechsten Sensor-Read)


================================================================================
KRITISCHE SIM-TO-SIM STOLPERSTEINE
================================================================================

  1. lin_vel_b [0:2]
     Muss im BODY FRAME sein, nicht world frame.
     Bei IMU-Integration driftet der Wert uebers Zeit.
     Empfehlung: Falls Gazebo /odom publisht, direkt nutzen und in
     body frame transformieren via IMU-Quaternion.

  2. gravity_b [6:8]
     Bei schneller Beschleunigung/Abbremsung verfaelscht durch Traegheitskraefte.
     Empfehlung: IMU-Quaternion direkt verwenden statt aus a_imu schaetzen.

  3. joint_pos_rel [12:29]
     Muss EXAKT pos - default_pos sein.
     Default-Werte sind fest: coxa = 0.0 rad, femur = tibia = 0.5 rad.
     Ein falscher Default-Wert erzeugt systematischen Bias in 6 Gelenken.

  4. last_actions [48:65]
     Bei Initialisierung mit zeros aber Roboter in anderer Startpose
     gibt es beim ersten Step einen Sprung. Zeros-Initialisierung ist
     korrekt solange der Roboter auch an der Default-Pose startet.

  5. Joint-Reihenfolge
     Isaac Lab alphabetisch  ≠  URDF-Reihenfolge  ≠  Gazebo /joint_states
     Die POLICY_TO_MOTOR / MOTOR_TO_POLICY Maps im ROS2-Node loesen das.
     Falsche Reihenfolge = Beine machen das was andere Beine sollen.

  6. Velocity-Commands [9:11]
     Waehrend Training: cmd_vx ist immer > 0.05 (kein Stillstand-Command).
     Fuer ROS2-Test: cmd = [0.3, 0.0, 0.0] ist ein guter Startwert.
     cmd = [0.0, 0.0, 0.0] war waehrend Training selten -> unbekanntes Verhalten.

================================================================================
ACTION VEKTOR — PYTHON AUFBAU (ROS2 Node Referenz)
================================================================================

  # Was die Policy ausgibt (nach TorchScript bundle.forward(obs)):
  raw_actions = bundle(obs_tensor)   # shape (18,), float, unbegrenzt

  # Schritt 1: Clippen
  clipped = np.clip(raw_actions, -1.0, 1.0)

  # Schritt 2: In Gelenkziele umrechnen (POLICY-Reihenfolge)
  q_target = DEFAULT_JOINT_POS + 0.5 * clipped

  # Schritt 3: Gelenkgrenzen
  q_target = np.clip(q_target,
                     DEFAULT_JOINT_POS - 0.5235,
                     DEFAULT_JOINT_POS + 0.5235)

  # Schritt 4: In MOTOR-Reihenfolge umordnen
  q_motor = q_target[MOTOR_TO_POLICY]

  # Schritt 5: Als absolute Gelenkziele publishen [rad]
  # -> /position_controller/commands  (Float64MultiArray)

  # Schritt 6: last_actions aktualisieren fuer naechsten Step
  last_actions = clipped
